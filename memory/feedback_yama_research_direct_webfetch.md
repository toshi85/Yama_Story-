# Yama リサーチは直接WebFetch必須

## 学習元事案（2026-05-25）

星野道夫台本作成時:
- エージェントBの要約レポートに依存して台本を執筆
- ユーザー指摘で `note 秋田しげと` 記事を直接WebFetchで取得した結果、エージェント要約には含まれていなかった重要独自情報を6件以上発見:
  - ロシア人ガイドが「兄弟2人」
  - 施設は「ロッジ（高床2階建て）」
  - 餌付け中止→飢餓状態の解釈
  - TBS報告書の距離記述が曖昧
  - 米国人写真家が8月1日以降「不在」
  - ヒグマ未解剖投棄説（諸説）
- ユーザーから「リサーチ品質が悪すぎる」と指摘

## 根本原因

1. エージェントの要約はトークン圧縮のため**重要情報を削ぎ落とす傾向**がある
2. エージェントが「重要」と判断したものと、台本に活かすべき情報は**必ずしも一致しない**
3. 要約レポートだけ見ると「網羅したつもり」になり、原典の細部にある独自情報を見逃す
4. 結果としてリサーチ品質が低下し、競合との差別化が弱まる

## ルール（強制）

### Rule 1: エージェント要約 + メインエージェント直接WebFetch の2段構え必須

```
✅ OK: エージェントで広く検索→主要ソース10件以上を直接WebFetchで原典確認
❌ NG: エージェント要約のみで台本執筆
```

### Rule 2: 引用フレーズは必ず原典確認

- 競合動画・他チャンネル・まとめサイトに掲載されているフレーズを、出典を遡らずに台本へ転載することは禁止
- 必ず一次資料（書籍・公式サイト・本人発信）でフレーズの原典を確認する
- 原典確認できない場合は **台本に書かない or 「と伝えられる」等の婉曲表現** にする
- 詳細: `feedback_yama_quote_source_verified.md`

### Rule 3: リサーチ着手前にソース一覧を計画化

- リサーチ着手時に、参照すべきソースのURL・取得方法（WebFetch/Playwright MCP）・期待情報を一覧化
- リスト全件を直接WebFetchで取得した後、初めて台本執筆に進む
- スキップする場合は理由を明示（paywall・404等）

### Rule 4: 必ず2倍以上のソース数を確保

- 競合動画が3本ある場合 → リサーチでは6本以上の独立ソースを直接取得
- 競合は1次資料の取捨選択を経た2次資料なので、独自情報を見つけるには競合より多くの原典に当たる必要がある

### Rule 5: ソースタイプの多様性確保

| ソースタイプ | 最低取得数 |
|---|---|
| 日本語Wikipedia | 1（必須） |
| 英語Wikipedia | 1（必須・英語圏独自情報の検出） |
| 公的機関・大学・学会 | 1以上 |
| 報道機関（新聞・雑誌オンライン） | 3以上 |
| 個人ブログ・note・専門サイト | 3以上 |
| YouTube/ニコ動 競合動画字幕 | 3以上（youtube-transcript-api使用） |

## 実装上の手順

### 着手前
1. リサーチ計画のソース一覧を作成
2. 各ソースのURL・タイプ・期待情報を表形式で明示
3. ユーザーに「これらを取得します」と先出し報告

### 取得時
1. メインエージェントが直接WebFetchで全ソース並列取得
2. paywall・404があれば即座に報告し代替ソース探索
3. エージェント委託は「広く検索」段階のみ。要約への依存禁止

### 取得後
1. 各ソースから「他の競合・他のソースには無い独自情報」を抽出
2. 抽出内容を台本に反映する判断（採用/不採用/婉曲化）
3. 引用フレーズには必ず `<!-- src: 出典名 取得日 -->` を添える

## 検証

- Yama_Story 関連タスク着手時、UserPromptSubmit hook で本ファイルへの誘導を表示
- 完了報告前に「直接WebFetchで取得したソース数」を明示

**Why:** エージェント要約のみで台本を書くと、競合との差別化に必要な独自情報を見逃す。秋田しげと記事1本で6+件の独自情報があった事実は、他の全ソースにも同様の見落としがあることを示唆する
**How to apply:** リサーチ着手時に本ファイルとセットで `feedback_yama_quote_source_verified.md` を必ず参照
